# 生产验收报告

> 三件事：**压测 → 可观测 → 备份恢复**。
> 全部在本地实测，数据与结论如下，脚本可复现。

## 一、压测

**工具**：`tools/loadtest.mjs`（零依赖，固定并发 worker 池抢任务队列）
**被测端点**：health / venues（鉴权+查库）/ sessions（子查询聚合）/ home（4 表并发）/ articles（分页）
**环境**：本机 Node 20 + MySQL 8（同机），数据库约 180 座位 / 10 预约 / 9 篇文章

### 结果

| 并发 | 请求数 | 耗时 | 吞吐 | 成功率 | P50 | P95 | P99 | Max |
|---|---|---|---|---|---|---|---|---|
| **50** | 2000 | 0.67s | **2999 RPS** | 100% | 13.8ms | **30.8ms** | 52.8ms | 73ms |
| **200** | 6000 | 1.68s | **3575 RPS** | 100% | 46.8ms | **96.9ms** | 102.8ms | 152ms |

**达标线**：P95 ≤ 300ms、错误率 ≤ 1% —— 两个档位都通过。

### 服务端视角（压测后读 `/api/stats`）

```
请求总数      8003
5xx 错误      0        错误率 0.00%
P50 / P95     36.4 / 87.2 ms
常驻内存      256.8 MB
```

### 最热路由（服务端统计）

| 路由 | 次数 | 平均耗时 |
|---|---|---|
| `GET /api/sessions` | 2001 | 35.7 ms |
| `GET /api/venues` | 2001 | 35.8 ms |
| `GET /api/health` | 1335 | 35.9 ms |
| `GET /api/home` | 1332 | 36.3 ms |
| `GET /api/articles` | 1332 | **72.2 ms** |

**发现的问题**：`/api/articles` 明显慢一倍 —— 原因是 `COUNT(*)` + `LIMIT/OFFSET` 两次查询，且 `articles` 只有 `(type, status, published_at)` 复合索引，分页深翻会退化。数据量到十万级时这里会先崩。

**已记录的优化方向**：把 count 改成缓存值或 `SQL_CALC_FOUND_ROWS` 的替代方案；深分页改游标（`WHERE published_at < ?`）。

### 复现

```bash
cd server
PORT=8788 RL_MAX=1000000 node src/index.js &     # 压测实例，解除限流
node ../tools/loadtest.mjs --url=http://127.0.0.1:8788 --c=50 --n=2000
```

报告落在 `reports/loadtest.json`、`reports/loadtest-200.json`。

## 二、可观测与告警

### 指标端点

| 端点 | 内容 |
|---|---|
| `GET /api/metrics` | Prometheus 文本格式，可直接接 Grafana |
| `GET /api/stats` | JSON 快照，压测/告警脚本用 |
| `GET /api/health/ready` | 就绪探针：数据库可查 **且** 迁移已执行才返回 200 |

采集内容：请求总数、5xx/4xx、按路由计数、延迟直方图（12 个桶）、P50/P95/P99、慢请求数、RSS。
路径做归一化（`/sessions/12/seats` → `/sessions/:id/seats`），避免维度爆炸。

### 告警规则

`tools/alert-check.mjs`，阈值可环境变量覆盖：

| 规则 | 阈值 | 级别 |
|---|---|---|
| `service_unreachable` | 就绪探针不可达 | critical |
| `not_ready` | ready≠true（如数据库断） | critical |
| `error_rate` | 5xx 占比 > 1% | critical |
| `latency_p95` | P95 > 300ms | warning |
| `slow_ratio` | 超 800ms 请求占比 > 5% | warning |
| `memory` | RSS > 800MB | warning |

### 三条路径都实测过

```
✓ 正常   请求 3　错误率 0.00%　P95 9.2ms　内存 68MB
✗ 越线   [WARNING] latency_p95 — P95 8.8ms > 1ms        ← 阈值调到 1ms 强制触发
✗ 不可达 [CRITICAL] service_unreachable — fetch failed   ← 指向死端口
```

告警以 JSON Lines 追加写入 `logs/alerts.log`：

```json
{"ts":"...","level":"critical","rule":"service_unreachable","detail":"fetch failed","target":"http://127.0.0.1:9999"}
```

### 复现

```bash
node tools/alert-check.mjs                      # 单次
node tools/alert-check.mjs --watch=30           # 守护模式
```

## 三、备份与恢复演练

**脚本**：`tools/backup.ps1`（结构+数据，校验核心表存在，保留最近 10 份）、`tools/restore.ps1`（干净重建库并校验非空）

### 演练过程（真实执行，不是走流程）

**1. 备份**

```
✓ 备份完成 venue_booking-20261110-042605.sql  (33 KB)  表: users, venues, bookings, articles
```

**2. 记录恢复前行数**

```
users 2　venues 4　bookings 10　articles 9　seats 180　tickets 5　orders 3
```

**3. 灾难模拟：DBA 误删**（真的执行了 `DELETE`）

```
users 2　venues 4　bookings 0　articles 0　seats 180　tickets 0　orders 0
```

**4. 恢复**

```
从 venue_booking-20261110-042605.sql 恢复…
恢复后行数:
  users      2
  venues     4
  bookings   10
  articles   9
  seats      180
✓ 恢复完成，所有核心表非空
```

**5. 全表校验 + 接口回归**

```
users 2　venues 4　bookings 10　articles 9　seats 180
tickets 5　orders 3　order_items 5　schema_migrations 4

/api/health/ready  HTTP 200
/api/sessions      HTTP 200
/api/home          HTTP 200
```

**恢复后数据与灾难前完全一致，服务无需重启即恢复可用。**

### 复现

```powershell
powershell -File tools/backup.ps1
powershell -File tools/restore.ps1 -File backups\venue_booking-<时间戳>.sql
```
