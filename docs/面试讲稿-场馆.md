## 二、一次下单的完整链路（白板必画）

```
① 前端 GET /api/sessions/:id/seats
   → sold  = order_items JOIN orders WHERE status='paid'
     lock  = seat_locks WHERE expire_at > NOW()
     合成四种状态：free / mine / locked / sold

② POST /api/sessions/:id/lock  { seatIds }
   事务内：
     1. 查这些座位在本场次是否已有 paid 订单 → 有就 409（防止锁已售的座）
     2. 删掉本人在本场次的旧锁（避免自己锁自己）
     3. 删掉所有 expire_at < NOW() 的锁（顺手清理）
     4. INSERT seat_locks (session_id, seat_id, user_id, expire_at)
   → 撞唯一索引 → ER_DUP_ENTRY → 409「座位刚被选走」

③ POST /api/orders  { sessionId, seatIds }
   事务内：
     1. 校验这些座位是本人在有效期内锁的
     2. 按 ticket_tiers 算金额（前端传什么都不看）
     3. 限购校验：本场已购（pending/paid）座数 + 本次 ≤ 6
     4. INSERT orders + order_items

④ POST /api/orders/:id/pay
   → payment.createPayment()（mock 立即成功 / wechat 返回支付参数）
   → mock：settleOrder() 置 paid、出票、删锁、写 payments 流水

⑤ 真实渠道：POST /api/pay/notify
   → provider.verifyNotify 验签 → 校验金额一致 → settleOrder（幂等）

⑥ 入场：GET /api/tickets/:code/qr.svg → 带签名的时效二维码
        POST /api/admin/tickets/redeem → 校验收到的码
```

**讲解要点**：这条链路上每一步都在回答同一个问题——**"客户端不可信时，正确性放哪"**。
答案是三层：唯一索引（库存）、服务端重算（金额）、幂等键（支付）。

## 三、六个核心机制（每题都要能讲 90 秒）

### 机制 1：预约防重 —— 用生成列 + 唯一索引，不用应用层判断

**问题**：同一场馆、同一天、同一时段，只能有一条有效预约。两个请求同时进来，`SELECT` 都查不到，然后都 `INSERT`，就重复了。

**做法**：表上加一个生成列，把"有效"编码成值：

```sql
active TINYINT UNSIGNED
  GENERATED ALWAYS AS (CASE WHEN status IN ('pending','approved') THEN 1 ELSE NULL END) STORED,
UNIQUE KEY uk_slot_active (venue_id, book_date, slot, active)
```

**为什么用 NULL**：MySQL 唯一索引里 **NULL 不参与去重**。所以取消/驳回后 `active` 变 NULL，同一时段可以再次预约；而 pending/approved 时 `active=1`，唯一索引就顶住了。

**代码位置**：`db/migrations/001_init.sql:36-38`

**追问：为什么不在应用层用事务 + 查询判断？**
能，但要靠锁。应用层判断要么 `SELECT ... FOR UPDATE` 锁行（可预约行不存在时锁不住，会退化成间隙锁，行为依赖隔离级别），要么靠分布式锁。唯一索引是**数据库无条件保证**的，代码写错了它还在。

**追问：为什么不用 Redis 分布式锁？**
这项目是单库，唯一索引已经够；引入 Redis 只为防重，等于多一个会挂的组件。真要多实例、要高并发，我会加 Redis 做前置削峰，但**最后一道仍然是唯一索引**。

### 机制 2：选座库存 —— `seat_locks` 的唯一索引就是库存

**问题**：180 个座位，多人同时选，谁先占到算谁的，还要能过期释放。

**做法**：
- 锁表 `seat_locks(session_id, seat_id, user_id, expire_at)`，对 `(session_id, seat_id)` 建唯一索引；
- 锁座是在**一个事务里**做四件事：查已售 → 删本人旧锁 → 清过期锁 → 批量 INSERT；
- 批量 INSERT 撞唯一索引 → `ER_DUP_ENTRY` → 返回 409；
- 有效期 15 分钟，靠 `expire_at` 判断，**不靠定时任务删**。

**代码位置**：`server/src/routes-tickets.js:131`（lock）、`:82`（seats 状态合成）

**座位四种状态怎么算**（`:121-123`）：

```js
let state = 'free';
if (soldSet.has(seat.id)) state = 'sold';                                  // 有 paid 订单
else if (lockMap.has(seat.id)) state = lockMap.get(seat.id) === uid
     ? 'mine' : 'locked';                                                  // 别人锁着/我锁着
```

**追问：两个人同时点同一个座，谁赢？**
数据库层面先拿到唯一索引插入权的人赢，另一个收 409。

**追问：为什么要先删「自己的旧锁」？**
用户改选座位时，旧锁不删会挡住自己（同一场次同一座位的唯一键还在）。先删再插，保证"我最终锁的 = 我想要的"。

**追问：为什么还要删「过期的锁」？**
唯一索引不区分过没过期。不清理的话，用户 15 分钟后回来发现锁还在库里，插不进去。清理条件下推成 `expire_at < NOW()`，顺手做。

**追问：15 分钟到期了，锁记录还在表里，会不会误判？**
不会。所有读的地方都带 `expire_at > NOW()`。表里的过期行是"垃圾"，不是"有效状态"。**读的时候判活，比定时删更可靠**（定时任务挂了也不出错）。

### 机制 3：订单金额只由服务端算

**问题**：前端可以改请求体，`amountCents` 传 1 分钱。

**做法**：下单接口**根本不读**前端金额，只按 `ticket_tiers` 里该场次该分区的价格重算：

```
座位 → venue_areas → ticket_tiers(session_id, area_id) → price_cents
金额 = Σ price_cents
```

**实测**：前端传 `"amountCents": 1`，返回的订单金额仍是真实票价（2 座 × 280 元 = 560 元）。

**代码位置**：`server/src/routes-tickets.js:168`（`/orders`）

**追问：那前端显示的合计怎么来的？**
前端也按同一套票档算，但它只是**展示**；最终以订单返回的 `amount` 为准，支付页显示的是服务端返回的值。

**追问：价格改了怎么办？**
已支付订单金额记在 `orders.amount_cents` 快照里，不会因为改票档而变化。退款退的是快照金额。

### 机制 4：支付 —— provider 抽象 + 幂等结算

**问题**：本地没有商户号，但不能让代码"假装支付成功"；以后接微信支付时不该改业务代码。

**做法**：定义一个支付接口，`mock` / `wechat` 两个实现：

```js
createPayment(order) → { channel, payParams }
verifyNotify(headers, rawBody) → { ok, orderNo, transactionId, amountCents }
refund(order, amountCents) → { ok, refundId }
```

- `mock`：本地直接返回成功，跑通「支付 → 出票 → 核销」全链路；
- `wechat`：缺配置时**抛 503**，不伪造成功；`createPayment` 的实现位置留空并写清步骤。

**幂等**：`settleOrder()` 是唯一结算入口，支付接口和支付回调共用它：
- 先 `SELECT ... FOR UPDATE` 拿订单行；
- 已是 `paid` 直接返回 `alreadyPaid`，不重复出票；
- 回调还额外校验**金额是否与订单一致**，不一致直接 400，不结算。

**代码位置**：`providers/payment.js`、`routes-tickets.js:37`（settleOrder）、`:332`（回调）

**追问：为什么回调不能只"记录一下"？**
第一版我就是只记录，评审立刻指出：接真渠道后用户付了钱、订单还是 pending、票不出——**付钱买到空气**。所以回调必须真的调用同一个 `settleOrder`。

**追问：重复回调怎么办？**
`payments` 表对 `(channel, transaction_id)` 建唯一索引 + `INSERT IGNORE`，加上订单状态判断，重复回调返回 `duplicated`，不会多出票。

### 机制 5：退票 —— 先校验、再占位、后打款

**问题**：如果先调渠道退款、再校验能不能退，真实渠道下就是资金事故——钱出去了，校验失败抛错回滚，数据库看起来像没退过，用户还能再退一次。

**做法**：拆成三段

```
① 事务：校验（归属 / 状态 / 24 小时窗口 / 有没有已核销的票）
        → UPDATE orders SET status='refunding'     ← 占位，挡住并发重复退
② 事务外：调 payment.refund()
        失败 → 回退 status='paid' + 写 refund_error，返回 503
③ 事务：status='refunded' + 票置 refunded + 写一条 refunded 流水
```

**为什么打款要放在事务外**：网络调用可能几十秒，事务里做会长时间占行锁，把同场次的其它下单全堵住。

**代码位置**：`routes-tickets.js:275`；状态机迁移 `db/migrations/007_refund_state.sql`

**追问：已核销的票还能退吗？**
不能。校验阶段查 `tickets WHERE order_id=? AND status='used'`，有就 409。**这条必须在打款之前**。

**追问：退款失败了怎么办？**
订单回退到 `paid`，`refund_error` 记录原因，前端提示可重试。不做自动重试（金额操作要人工确认）。

### 机制 6：对账 —— 订单和流水必须能对上

**问题**：只靠 `orders` 一张表，出了错无法交叉验证。

**做法**：新增 `payments` 流水表（每次结算/退款写一条），提供 `/admin/reconcile?date=` 查四类差异：

| 类别 | 含义 |
|---|---|
| `missing` | 订单已支付，但没有流水 |
| `mismatch` | 流水金额 ≠ 订单金额 |
| `duplicated` | 同一订单多条成功流水 |
| `orphans` | 有流水，但订单不存在 |

`balanced` 必须同时满足：四类都为空 **且** 总差额为 0。

还有命令行版 `tools/reconcile.mjs`：账不平退出码为 2，可以直接挂 CI。

**代码位置**：`routes-tickets.js:391`、`tools/reconcile.mjs`

**追问：为什么口径要对齐？**
踩过坑：一开始流水按 `created_at` 取日期、订单按 `paid_at` 取，两边差一天就永远不平；还混进了当天已退款的订单。后来统一成「只统计 `status='paid'` 且 `DATE(paid_at)=当日`」。

## 四、前端要能讲的四件事

### 1. 选座页的轮询与倒计时

- 每 10 秒拉一次座位状态，`document.visibilityState !== 'visible'` 时跳过（省流量、省请求）；
- 锁座后倒计时**不是本地记 15 分钟**，而是读服务端返回的 `myLockExpireAt`（`SeatSelect.vue`），这样刷新页面倒计时不归零；
- 结算栏 `position: sticky` 固定在底部，不遮挡座位。

### 2. 二维码为什么用 blob

给二维码接口加了鉴权后，`<img src="/api/tickets/xxx/qr.svg">` 全部 401——**`<img>` 发不出 `Authorization` 头**。
改成 `fetch` 带头取 SVG → `URL.createObjectURL(blob)` → 塞给 `<img>`，组件卸载时 `revokeObjectURL` 释放。

### 3. 生产白屏的原因

Vite 产物是 `<script type="module" crossorigin>`，**带了 `crossorigin` 就强制走 CORS**，同源也一样。
服务端 `CORS_ORIGINS` 为空时没返回 `Access-Control-Allow-Origin`，脚本被拦，整页白。
修法：`cors()` 的 origin 回调里，白名单为空时视为「单端口同源部署」直接放行。

### 4. 后端富文本编辑器

零依赖：`contenteditable` + `document.execCommand`（`RichEditor.vue`），支持加粗、无序列表、二级标题、引用、插入链接与图片；图片先调 `/admin/upload` 拿 URL，再 `insertImage`。

**追问：execCommand 不是废弃了吗？**
是，MDN 标了 deprecated，但主流浏览器仍支持。换成 ProseMirror/Slate 要引几十 KB 依赖并重做数据模型，收益不抵成本。**这是我明确记下的技术债**。

## 六、三个真实 bug（讲这个最显功力）

### bug 1：锁已售座位还能成功（业务逻辑漏洞）

锁座接口原来只依赖唯一索引，不判断"这个座是否已经被别人买走"。已售座位没有锁记录，所以能插进 `seat_locks`。
**修法**：事务里先查 `order_items JOIN orders WHERE status='paid'`，命中就 409。

### bug 2：多场次座位串了（只有加新功能才会暴露）

加"后台自建场次"后，新场次座位图返回了 360 个座位（应为 180）。原因：`/sessions/:id/seats` 查 `seats` 时没限定本场次的分区。
**修法**：`seats` JOIN `ticket_tiers` 按 `session_id` 过滤。
**这个 bug 只在"多场次"这个新能力出现后才存在**——原来 2 场共用一套座位，一直没暴露。

### bug 3：`venues.cover` 不在迁移脚本里（schema 漂移）

本地库有这一列，迁移脚本里没有——当初手动加的。后果：**任何全新环境导入场馆数据都报 `Unknown column 'cover'`**。
**修法**：新增 `008_venue_cover.sql`，用 `information_schema` 守卫，已有该列的环境自动跳过。
**这条最能说明"照文档部署跑不起来"是怎么发生的。**

## 七、主动承认的边界（被问"有什么不足"就这么答）

1. **微信支付只留了接口位**：没有商户号，`verifyNotify` 的验签没实现（代码里明确 throw，不返回假成功）。
2. **没有用户自助注册 / 实名**：账号是种子数据，真实场景要接学号或企业微信。
3. **图片存本地磁盘**：多实例部署会坏，应该换对象存储。
4. **限流和轮询是单机内存**：多实例要换 Redis。
5. **富文本用 execCommand**：技术债。
6. **对账只覆盖"当日已支付"**：没有跨日、跨渠道的完整账务。

> 讲这些不是自曝短板，是**证明我知道系统边界在哪**。面试官最怕的是"他以为这套东西能上生产"。
