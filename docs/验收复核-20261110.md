## 与预期不一致的项（6 处，均不影响判据）

1. **#10 构建耗时**：文档写 `~1s`，实测 `2.94s`（106 模块）。构建成功、退出码 0，属机器差异，非缺陷。
2. **#7 核销文案**：预期「已使用」，实际「票码无效或已使用」；且**无效码与已用码返回完全相同的 code/文案**（都 409/40904），现场无法区分"码打错了"和"这票已核销"。建议拆成两个 code。
3. **#4 轮播箭头**：浏览器默认视口 738×931 时，`.hero-arrow` 被 `@media (max-width:900px)` 设成 `display:none`，截图里只剩指示点和计数；视口放宽到 1440px 才出现 ‹ ›。文档"有箭头"未标注视口条件，属响应式设计的预期行为，但清单表述不严谨。
4. **#1 响应头名**：文档 `X-Request-Id`，实际 `X-Request-ID`，大小写差异，HTTP 头不区分大小写。
5. **#3 指标行数**：`venue_requests_total` 只有一条聚合值（无 label 维度），推送 Prometheus 后无法按路由/状态码切分，只能看总量。

## 清单外发现

1. **非法 JSON 请求体返回 500 而不是 400**：`POST /api/admin/tickets/redeem` 带 `{"code":invalid}` → `HTTP 500 {"code":50000,"msg":"服务器开小差了..."}`。`express.json()` 解析失败被兜底错误处理器吞成 500，客户端拿到"服务器故障"而非"请求格式错误"，会误导排查。
2. **错误响应字段不一致**：`fail()` 产生的 409 响应体无 `requestId`（`{"code":40904,"msg":"票码无效或已使用"}`），`AppError` 产生的 400 响应体有 `requestId`。带 `X-Request-ID` 头能对上日志，但响应体里缺字段，排障时要额外查头。
3. **权限与空值边界正常**：学生 token 调核销 → 403/40300「无权限」；空票码 → 400/40000「请填写核销码」；重复支付 → `alreadyPaid:true` 且不多出票（11 → 11，确认幂等）。
