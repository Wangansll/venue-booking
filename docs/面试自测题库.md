## A. 开场与定位（5）

**A1. 用一句话介绍这个项目。**
【答】校园场馆官网 + 票务系统：前台能约场地、选座买票、看活动新闻，后台能管场馆、发内容、审预约、核销票。前端 Vue 3 + TS，后端 Node + MySQL，已上线。

**A2. 你在这个项目里负责什么？**
【答】全部。从建表、写接口、做页面到部署上线都是我自己做的，所以能讲清每一步为什么这么做。
（**不要说**"我负责前端部分"——那样后面所有后端问题都会被追问"这是谁做的"）

**A3. 为什么做这个项目？**
【答】学校里约场地要跑办公室、看 Excel、还经常撞车。我想验证一件事：能不能用一条数据库约束把"撞车"这件事从根上解决，而不是靠人工。
做完发现真正难的不是页面，是"钱和库存不能错"。

**A4. 这个项目最大的技术难点是什么？**
【答】并发下的正确性。具体是三个点：座位库存（两个人抢同一座）、订单金额（前端可篡改）、支付幂等（重复回调不能重复出票）。
这三个都不是"写得出来"的问题，是"写错了但测试不出来"的问题。

**A5. 如果重做一遍，你会改什么？**
【答】三件事：① 用户体系从种子数据换成真实注册 + 实名；② 图片从本地磁盘换对象存储；③ 富文本从 `execCommand` 换掉。
（**先给三条，再挑一条讲理由**——按顺序说，别一次全讲完）

## B. 场馆 · 并发与数据（12）

**B1. 同一时段两个人同时预约，怎么保证只有一条？**
【答】数据库唯一索引。表上有生成列 `active = (status IN ('pending','approved') ? 1 : NULL)`，唯一键 `(venue_id, book_date, slot, active)`。
有效预约时 `active=1` → 撞键；取消/驳回后 `active=NULL` → NULL 不参与去重 → 可重约。

**B2. 为什么用 NULL 而不是 0/1 两态？**
【答】因为 MySQL 唯一索引里 NULL 可以重复。用 0/1 的话，取消后 `active=0` 也会撞键，同一时段就永远只能约一次。

**B3. 为什么不在应用层判断"先查再插"？**
【答】并发下两个请求都查不到、都插入，必然重复。要防就得加锁；行不存在时锁不住，会退化成间隙锁，行为还依赖隔离级别。唯一索引是数据库无条件保证的。

**B4. 座位库存怎么实现的？**
【答】`seat_locks(session_id, seat_id, user_id, expire_at)` 表，对 `(session_id, seat_id)` 建唯一索引。
锁座在一个事务里：查已售 → 删本人旧锁 → 清过期锁 → 批量 INSERT。撞唯一索引就返回 409。

**B5. 锁为什么是 15 分钟？到期怎么释放？**
【答】15 分钟是"够用户填完支付信息"的经验值。到期**不靠定时任务删**，所有读的地方都带 `expire_at > NOW()`——读的时候判活，定时任务挂了也不出错。

**B6. 那过期记录不会越积越多？**
【答】会。所以锁座事务里顺手 `DELETE FROM seat_locks WHERE expire_at < NOW()`，借高频操作做清理。（真上量会换成定时任务或分区，但这个量级够用）

**B7. 座位图上的四种状态怎么算出来的？**
【答】两次查询合成：
- `sold`：`order_items JOIN orders WHERE status='paid'`
- `mine` / `locked`：`seat_locks WHERE expire_at > NOW()`，看 `user_id` 是不是自己
- 都不在 → `free`

**B8. 用户改选座位，旧锁怎么办？**
【答】锁座事务里先 `DELETE ... WHERE session_id=? AND user_id=?` 删掉本人的旧锁，再插新的。不删的话唯一键会挡住自己。

**B9. 加"后台自建场次"功能时踩过什么坑？**
【答】新场次座位图返回了 360 个座位（应该 180）。因为查座位时没限定本场次，把别的场次的座位也查出来了。修法是 `seats JOIN ticket_tiers ON session_id`。
这个 bug 只在多场次出现后才存在——之前 2 场共用一套座位，一直没暴露。

**B10. 数据库用的什么？为什么线上是 MariaDB？**
【答】本地 MySQL 8，线上那台机器（Debian 13）仓库里只有 MariaDB 11.8。我核过 SQL：没有 `utf8mb4_0900` 这种 MySQL 8 专属排序规则，生成列用标准 `GENERATED ... STORED`，MariaDB 完全兼容。
（**这句"我核过"很重要**，说明不是随便换的）

**B11. 有多少张表？**
【答】16 张业务表，加上迁移记录表。主要分四块：用户/场馆/预约、内容、票务、支付流水。

**B12. 事务用在哪些地方？**
【答】四处：锁座、下单、结算出票、退款占位。共同特征：**一次操作改多张表且不能半途而废**。

## C. 场馆 · 支付 / 退款 / 对账（10）

**C1. 前端能改订单金额吗？**
【答】不能。下单接口根本不读前端金额，只按 `ticket_tiers` 重算。
实测：前端传 `amountCents: 1`，订单金额仍是真实票价。

**C2. 支付是怎么抽象的？**
【答】定义三个方法：`createPayment` / `verifyNotify` / `refund`，`mock` 和 `wechat` 两个实现。
`mock` 本地跑通全链路；`wechat` 缺商户号时**明确抛 503**，不伪造成功。

**C3. 为什么支付回调不能只是"记录一下"？**
【答】第一版我就是只记录，评审指出：接真渠道后用户付了钱、订单还是 pending、票不出——**付钱买到空气**。
所以回调必须调用和支付接口**同一个** `settleOrder()`。

**C4. 重复回调会不会重复出票？**
【答】不会。`settleOrder` 先 `SELECT ... FOR UPDATE`，`status='paid'` 直接返回 `alreadyPaid`；
`payments` 表对 `(channel, transaction_id)` 建唯一索引 + `INSERT IGNORE`，双保险。

**C5. 回调金额和订单金额不一致怎么办？**
【答】直接 400 不结算。这是防"改金额重放"的最后一道。

**C6. 退票的顺序为什么这么讲究？**
【答】必须**先校验、再占位、后打款**。
反过来（先打款再校验）在真实渠道下是资金事故：钱出去了、校验失败抛错回滚、数据库看起来没退过，用户还能再退一次。

**C7. `refunding` 这个中间态有什么用？**
【答】占位。从 `paid` 改成 `refunding` 后，并发来的第二个退款请求会被挡住（状态不合法），避免重复打款。

**C8. 退款失败怎么处理？**
【答】回退到 `paid`，把原因写进 `refund_error` 字段，接口返回 503。不做自动重试——金额操作要人工确认。

**C9. 已核销的票能退吗？**
【答】不能。校验阶段查 `tickets WHERE order_id=? AND status='used'`，有就 409。
**这条必须在打款之前**，否则钱退出去票又用了。

**C10. 对账查什么？**
【答】四类差异：`missing`（付了钱没流水）、`mismatch`（金额不符）、`duplicated`（重复流水）、`orphans`（流水找不到订单）。
`balanced` 还要满足总差额为 0。命令行版账不平退出码 2，可挂 CI。

## D. 场馆 · 前端（10）

**D1. 选座页怎么做状态同步？**
【答】每 10 秒轮询座位状态；`document.visibilityState !== 'visible'` 时跳过。切换页面回来会立刻再拉一次。

**D2. 刷新页面倒计时会归零吗？**
【答】不会。倒计时不是本地记 15 分钟，而是读服务端返回的 `myLockExpireAt`，用到期时间减当前时间算剩余。

**D3. 二维码为什么用 blob？**
【答】加了鉴权后 `<img src>` 全部 401——**`<img>` 发不出 Authorization 头**。改成 `fetch` 带头取 SVG → `createObjectURL` → 塞给 `<img>`，卸载时 `revokeObjectURL`。

**D4. 生产环境白屏，你怎么定位的？**
【答】先确认 HTML 和 JS 都能 200（用 curl 直连），再截图对比——本地正常、线上白。然后看控制台：`<script type="module" crossorigin>` 带 `crossorigin` 就强制走 CORS，同源也一样；服务端白名单为空没返回 `Access-Control-Allow-Origin`，脚本被拦。

**D5. 修法是什么？**
【答】`cors()` 的 origin 回调里，白名单为空时视为「单端口同源部署」直接放行。因为前端和 API 在同一个域名下，本来就不需要跨域限制。

**D6. 设计令牌具体是什么？**
【答】一套 CSS 变量管颜色、间距、圆角、字号（`--brand-500`、`--s-6`、`--shell-max` 等），组件只引用变量。改主题只改一处。

**D7. 响应式怎么做的？**
【答】两档断点：1080px 侧栏收成抽屉（汉堡菜单），900px 单列化。用 Grid 做应用外壳，卡片用 `auto-fill` 自适应列数。

**D8. 轮播做了哪些交互？**
【答】箭头、指示点、左右方向键、悬停暂停自动播放；默认从中间那张开始（视觉重心更稳）。

**D9. 空状态和骨架屏在哪用？**
【答】列表页加载时显示骨架屏，无数据显示空状态；首页各区块也有占位。

**D10. 富文本编辑器怎么实现的？**
【答】`contenteditable` + `execCommand`，支持加粗、无序列表、二级标题、引用、插入链接与图片；图片先调上传接口拿 URL 再 `insertImage`。
**追问就承认**：`execCommand` 已废弃，这是技术债。

## E. 场馆 · 工程化（8）

**E1. 配置校验做了什么？**
【答】生产环境 `JWT_SECRET` 不足 32 位、或含 `change-me` 这类弱口令，启动直接退出。不是警告，是拒绝启动。

**E2. 日志怎么设计的？**
【答】JSON 结构化，每个请求一个 `X-Request-Id` 贯穿中间件、业务、错误处理，出问题能按 ID 串起来。

**E3. 错误码为什么单列一张表？**
【答】前端要按码分支处理，不能靠匹配中文文案。5xx 统一不外泄堆栈，只回"服务器开小差了 + requestId"。

**E4. 限流怎么做的？**
【答】滑动窗口，按 IP，默认 120 次/分钟。**已知边界**：内存实现，多实例会各自计数，要换 Redis。

**E5. 迁移脚本怎么防重复执行？**
【答】`schema_migrations` 表记录文件名 + checksum。已执行且 checksum 一致就跳过；checksum 变了会报错——防止有人改历史迁移。

**E6. 你加了什么指标？**
【答】`/api/metrics` 输出 Prometheus 文本（请求数、错误率、延迟直方图、按路由计数、RSS），`/api/health/ready` 做就绪探针（数据库可查 + 迁移已执行）。

**E7. 压测数据是多少？**
【答】50 并发 2000 请求：P95 30.8ms、约 2999 RPS；200 并发 6000 请求：P95 96.9ms、约 3575 RPS，错误率 0。
**必须补一句**：这是本机 MySQL + 小数据量的结果，不代表生产容量。

**E8. 备份恢复做过演练吗？**
【答】做过。删光 4 张业务表 → 从备份恢复 → 行数与灾难前完全一致，接口不用重启就恢复。
**没演练过的备份等于没备份**——这句可以讲。

## F. 工厂（10）

**F1. 为什么不用框架？**
【答】想自己把"状态变了怎么更新界面"写一遍。代价是要记得手动触发布局，收益是体积小、零构建、启动快。

**F2. 生图要几十秒，怎么处理？**
【答】提交接口只登记并返回 `jobId`，前端轮询状态接口拿增量结果。不用 WebSocket 是因为"一次任务一次结果"，轮询够用且断线自愈。

**F3. 取消是怎么做的？**
【答】`AbortController` + `fetch` 的 `signal`，真取消请求；同时用递增 id 校验"回来的结果是不是当前任务"，否则丢弃。

**F4. 只 abort 不校验 id 会怎样？**
【答】会出竞态：取消后发起新请求，旧请求的响应如果晚到，会把旧结果贴上去。我踩过这个坑。

**F5. 九宫格怎么导出的？**
【答】Canvas 3×3 布局，`drawImage` 逐张画，再 `toBlob` 生成 PNG 下载。不引图像库，也不引 html2canvas——本来就有原图，直接画更准。

**F6. Canvas 导出会失败吗？**
【答】会。画了跨域图且没带 CORS 头，canvas 被标记污染，`toBlob` 抛安全错误。所以图片加载要带 `crossOrigin`，或者后端代理成同源。

**F7. 画风怎么实现的？**
【答】13 档画风对应 13 条英文风格提示词后缀，拼在用户输入后面。

**F8. 分享链接怎么做的？**
【答】`POST /api/share` 存一份结果返回 `sharecode`；别人用 `/?sharecode=xxx` 打开，前端 `GET /api/share/:code` 拉那一整套。

**F9. 后端用了什么？**
【答】Node 原生 `http`，自己处理路由分发、请求体解析、CORS。6 个接口：会话、生成、生成状态、创建分享、读取分享、作品列表。

**F10. 密钥怎么管的？**
【答】生成接口读 `process.env.PROVIDER_API_KEY`，没配时返回 `missing_provider_key` 而不是 500。
仓库里没有任何真实密钥，`*.key` 和 `.env` 都在 `.gitignore`。

## G. 压力题 / 陷阱题（8）

**G1. 你这两个项目是不是抄的？**
【答】代码在 GitHub 上，你可以看提交记录和文件时间。而且我能讲清每一处为什么这么写——比如为什么预约防重用生成列而不是状态字段，抄的话讲不出这些取舍。

**G2. 一个月做两个项目？**
【答】场馆是主力，占绝大部分时间，做了十几轮迭代；工厂是周末做的小工具，前端就一个 `app.js`。不是同时从零开始。

**G3. 你说的并发问题，实际有多少人同时在抢？**
【答】演示环境没有真实流量。**但我用压测和并发脚本验证过**：50/200 并发下 P95 和错误率都有数据，唯一索引的 409 是实测出来的，不是推演。

**G4. 这套东西能上生产吗？**
【答】不能直接上。缺三样：真实支付资质、备案与隐私协议、运维体系（监控告警通道、对象存储、多实例下的限流）。
**能说的是**：代码层面的正确性、可观测性、可恢复性做到了准生产，缺的是资质和运营。

**G5. 你这个"对账"有必要吗？**
【答】有。只靠订单表，出了错没法交叉验证。加流水表后，四种异常都能查出来——我实测过删一条流水、改一条金额，都能定位到具体订单。

**G6. 为什么订单金额不在前端算？**
【答】前端算的是"给用户看的"，后端算的是"真正收钱的"。前端可以被改，网络可以被重放，只有服务端重算才是事实。

**G7. 如果让你现在加"退票审核"（运营审核后再退），怎么改？**
【答】把 `refunding` 前面插一个 `refund_pending` 状态：用户申请 → 状态置 `refund_pending` → 后台审核 → 通过才进 `refunding` 打款。**关键是状态机加一层，打款顺序不变**。

**G8. 你怎么保证自己写的代码是对的？**
【答】三层：① 23 个接口测试覆盖主链路（下单、回调、限购、退款、对账）；② 关键约束放在数据库（唯一索引、外键、金额服务端算），写错也挡得住；③ 上线后自己手点一遍全流程，包括失败路径。

## 最后：三句话把两个项目收尾

> **场馆**练的是"数据不能错"——并发、金额、幂等，全靠数据库兜底。
> **工厂**练的是"交互不能乱"——异步任务、取消、竞态，全在前端自己扛。
